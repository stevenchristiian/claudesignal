### Tape convention — a one-hour offset was caught and corrected before it reached the build
The first tape script took the N-day base as the candle **opening** at `LAST - N*24h + 1h`, which is one hour
off. It returned BTC 7d as **-3.6208%** where the correct figure is **-3.4220%**. Caught by re-running the
corrected script against the **previous** build stamp and requiring it to reproduce that build's published
table — which it did, exactly, on all six names and all five percentage columns.

> **The base for an N-day return is the close of the candle OPENING at `LAST - N*24h`, where `LAST` is the
> opening hour of the last completed candle.** Verify any new tape script by reproducing the previous build's
> published percentages before using it. This is the §7 "run the assertion against the previous build" rule
> applied to a data script rather than to a validator, and it worked the same way.

> **Generalise, and this is the sharpest version of the family yet.** The 09-25 entry established that a bar

> Two publishers can both be measuring "quarterly protocol revenue", in dollars, for the same quarter, and

> calibrated in. Record the vendor beside every bar, not just the number.**

**Decision needed before the completed quarter lands:** does this branch read the OAK-convention series (which
