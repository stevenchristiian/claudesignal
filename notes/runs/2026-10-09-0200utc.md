### THE ROLL-OFF SIGN PUZZLE IS SOLVED — the old reference was the wrong object

For two runs (10-06, 10-07) this deck could not reconcile the sign of the roll-off step with the
departing session, and 10-08 noted the day-level figure "bounds the sign but not the size" (predicted
1.1172pt against a measured 2.3675pt, **2.12x off**). **The reference was wrong.** The day-level *peer
median* is a different object from the *window median*; what the roll-off step measures is BNB
against **the asset that is the window median**.

| Run | BNB, departing day | Window-median asset, same day | Predicted roll-off | Measured | Agreement |
|---|---|---|---|---|---|
| **2026-10-09** | +0.3264% | **SOL** +1.2457% | **+0.9193pt** | **+0.8829pt** | **0.0364pt** |
| 2026-10-08 (control) | +1.1830% | **SOL** -1.1724% | **-2.3554pt** | **-2.3675pt** | **0.0121pt** |

On the day-level peer median this run would again have looked "wrong-signed": the day's peer median
was **ETH +0.9892%**, so BNB *lagged* by 0.6628pt, and a lagged departing day should narrow the margin
while the roll-off step **widened** it.

> **Sanity-check a trailing-window relative margin against the departing-day return of the asset that
> is the window median, never against the departing day's own peer median.** The first predicts both
> sign and magnitude to within ~0.04pt on both runs tested; the second got the size wrong by 2.12x on
> one run and the sign wrong on the other. **Two runs of "the branch is unexplainable" were two runs
> of comparing the right number to the wrong object** — the §5.5 family, inside this deck's own
> arithmetic rather than in a publisher's.
> **This narrows but does not retire the median-identity decision.** The prediction works *because*
> the median held identity across old -> overlap; when it changes there (as on 10-07), no single
> asset's departing-day return can explain the step, which is exactly the defect.

### A NEW TOOLING GOTCHA: `$(...)` STRIPS TRAILING NEWLINES, SO A SHA BUILT ON IT IS OFF BY ONE BYTE

The polling loop compared `printf '%s' "$OUT" | sha256sum` against the built file's sha and **never
reported a match**, while printing `bytes=59746` against a built **59,747** and the correct new
`AS_OF`. **The publish was fine; the assertion was wrong.** Command substitution strips trailing
newlines, so `$OUT` held the served page **minus its final newline**, and the hash could not match by
construction.

> **Never verify a published artefact by hashing a shell variable. Download to a file and compare
> files** (`curl -o`, then `sha256sum` and `diff`). **The signature of this bug is a one-byte
> shortfall with a correct as-of label; the signature of a bad publish is a STALE as-of label.** They
> are easy to tell apart, so tell them apart before reporting a failed publish. §7's
> audit-the-assertion rule applies to the publish check too, not only the pre-publish ones.
> Sibling of 10-08's note that an empty background log is not evidence that nothing happened:
> **both are cases where the measuring apparatus, not the thing measured, produced the alarming
> reading.**

### AND A SECOND ONE: DO NOT `pkill` A PATTERN THAT MATCHES YOUR OWN SHELL

Stopping the background poller with `pkill -f "stevenchristiian.github.io"` **also killed the shell
